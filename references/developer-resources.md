# Developer dependencies and runtimes

| Area | Examine | Preserve or validate |
| --- | --- | --- |
| Homebrew | Identify active prefixes, installed formulae and casks, `brew cleanup --dry-run`, `brew autoremove --dry-run`, `brew missing`, `brew services list`, and relevant reverse dependencies. Suppress automatic updating for a local audit. | Check current versions and working services before any removal. Report upgrades separately, with catalog freshness if relevant. Parallel major runtimes can have different dependents. |
| npm / npx | Identify the active Node and npm binaries, npm global prefix, top-level globals, per-project lockfiles and the exact npx cache package version. Inspect command links without chasing broken targets through unrelated locations. | A global version check sends package names to a registry. Use only an authorized registry and known-public names for public checks. Verify both running and configured callers before moving shared cache entries. |
| Project dependency trees | Check workspace membership, lockfile, project reuse, process working directories and open files. Use offline dependency inventory where possible. | `extraneous` alone can flag optional/platform packages that the lockfile still describes. Keep the manifest and lockfile for any approved rebuildable tree. |
| pnpm / uv / Python | Check the effective cache/store path for each installed version and check project metadata, interpreter links, tool environments, and open files. | Identify managed interpreters and installer-linked environments before store pruning. Keep stores still referenced by a project or process. Use manager-supported cleanup where its exact scope is authorized. |
| Playwright and similar tools | Inspect browser registrations and package versions. Check which projects, AI tools and skills share the browsers. | Treat browser binaries as downloads with a rebuild cost. Old entries require usage evidence and a validated replacement where relevant. |
| Xcode | Compare DerivedData, simulator runtimes/device data, archives and project caches separately. | Use Xcode component management for simulator runtimes. Keep release archives and simulator user data unless specifically included. |
| Docker / OrbStack | Use the running engine's `docker system df -v` and targeted container/image/volume information when available. | Keep named volumes and databases until specifically identified and authorized. If the daemon is unavailable, report missing visibility. Avoid blanket prune or touching the VM's disk files. |

When removing older tool versions, confirm the newer tool works before dropping the older cache. Verify representative CLI versions or an actual read-only operation after applying the change.

Primary references: [Homebrew manpage](https://docs.brew.sh/Manpage), [npm cache](https://docs.npmjs.com/cli/commands/npm-cache), [pnpm store](https://pnpm.io/cli/store), [uv caching](https://docs.astral.sh/uv/concepts/cache/), [Playwright browsers](https://playwright.dev/docs/browsers), [Xcode components](https://developer.apple.com/documentation/xcode/downloading-and-installing-additional-xcode-components), [Docker storage usage](https://docs.docker.com/reference/cli/docker/system/df/).
